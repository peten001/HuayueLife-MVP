## 数据与金额

- 2026-10-17 用户已授权将下述未发送减菜修复提交、推送并部署，候选版本 `kds-unsent-returns-20261017-v3`。此前“本地／未发布”为开发阶段记录；实际切换及验证结果见 [RELEASE.md](RELEASE.md)。仅需更新两项 API 服务，不改数据库或前端。
- 2026-10-17 未发送减菜边界（本地，未发布）：收银仍保留录单修改审计及当前退菜展示；厨房只对已成功入 KDS 任务的数量减少产生 RETURN。尚未发送、通知事务失败／回滚的菜品删减，不创建 KDS 退菜任务或操作。通知成功以服务端事务提交并创建／更新厨房任务为准；前端请求超时不等于服务端一定失败，仍沿用原幂等键确认结果。
- 同菜合并跨原订单时，使用锁定菜品行的 productionNotifiedQuantity 先在全部可调来源中消耗未发送份数，再按原订单状态／ID 顺序减少已发送份数。单行同时扣未发和已发时合并为一次收银变更，厨房仅记录实际减少的已发数量。例如原点 5 份、已发 3 份，减到 3 份不产生厨房退菜；再减到 2 份仅产生 1 份厨房退菜。收银仍按累计删减记录和有效数量计费，历史不抹除。
- OrderItem.quantity 继续表示有效、可计费数量；subtotalVnd 为有效数量的金额。新增 returnedQuantity 累计已退数量，原点数量由两者之和表示。全退保留原行，quantity/subtotal 为零。
- 已接单后的退菜在旧单菜退菜接口和当前整桌目标态对账中保持一致；未接单草稿减菜仍可删除。未增加已结账后的退菜或自取／配送的单菜退菜入口。
- 全退后重新点同一道菜创建新菜品行，不复活已退的行。部分退后继续加菜保留既有退数量。
- 原通知及 OrderStatusLog/KdsOperation 不删除；KDS 有效制作／传出数量仍受有效任务数量约束，退掉的已做／已传数量新增累计字段保存。操作版本变化会拒绝旧批次，幂等重试不重复退菜。
- 传菜关闭时仍按既有自动出餐规则处理；退菜量不重新进入待传。厨房操作不收款。
- 全退不计应收；保留现有折扣／抹零重算与整桌退空自动释放规则。普通账单打印仅包含数量大于零的计费行，避免向原打印契约传入零数量。

## 展示与历史

- 收银主账单：部分退菜显示原点／已退／有效，全退加删除线、显示退数量及零金额，无加减按钮。
- Canonical API 的 items 只含有效行；新增只读 returnedItems，避免退菜记录影响对账目标、退空判断或重下单。
- KDS 标准划菜与订单进度保留退菜任务；全退加删除线并显示退数量，无划菜／传菜按钮。汇总待做、待传及超时统计不计算全退任务。当前看板仍沿用原任务保留窗口；完整历史不依赖看板的近期记录上限。
- 2026-10-17 补齐汇总划菜：保留仍在制作的桌／订单的部分／全退信息，卡片标明累计已退数量，右侧与标准划菜一致显示原点／已退／有效和制作、传菜历史。全退行的菜名加删除线，桌号保持正常；只有待做量参与批量划菜，待做任务在只读退菜行前显示。只有退菜记录的菜品分组，仅在所属桌／订单的当前档口仍有其他待做菜品时保留，否则从制作队列退出并在进度／历史中查看。
- 退菜后 KDS 沿用 5 秒自动刷新；刷新时把已选划菜／传菜数量限制为最新可操作量，全退后清除选择，冻结中的不确定请求仍保持原请求键和原载荷。收银即时预览累计退菜并保留全退行，普通草稿减菜不伪造退菜，明确失败时回滚。
- 完整订单展示部分及全退菜品，包含同次用餐中退空而取消的子单。整桌全退关闭后也有零应收的已取消历史。销售单数与财务汇总不因退菜记录重复计算。
- 中英越文案、菜名切换、压缩菜图规则与独立 KDS 地址保持。
- 历史已经硬删除的原菜品不自动补造，既有退菜日志继续保留；新增累计字段从零开始，不声称还原历史全部制作数量。
