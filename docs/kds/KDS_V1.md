## 使用

直接打开独立 KDS 地址登录。按用户最新要求，电脑收银、手机导航及“我的”账户菜单均不设置 KDS 入口，收银保持原来的四项导航。两边使用同一商家员工账号、分别登录；KDS 使用 `yunqiao_kds` 存储前缀，收银保留原 `yunqiao_cashier` 前缀。KDS 登录后进入厨房，不加载桌台收银工作区；退出 KDS 不清除收银登录。

首次使用由店主／经理在“厨显设置”开启 KDS，设置档口、超时分钟数及菜品分类归属。未分配分类进入第一个档口；已入厨任务保留原档口，分类设置影响新任务。数据库迁移不会自动给任何门店开通 KDS。仅保存门店设置保留短时成功提示；划菜与传菜点击后直接生效，无确认弹窗或“已更新”提示。

顶部：档口、全部／堂食／商家配送／到店自取、搜索；刷新、声音、设置、全屏、退出及时间靠右成组。左上沿用收银的门店照片、名称及营业时段状态，时间下显示越南日期和星期。启动与登录页使用 YunQiao KDS 品牌。语言选择位于“厨显设置”，支持中文／English／Tiếng Việt，即时切换并记住当前设备的选择；所有员工都可切换语言，门店开关、档口和分类配置仍仅由店主／经理维护。菜名、档口名及顾客备注保持门店原配置内容。设置只保留顶部齿轮入口。

左侧：标准划菜、汇总划菜、待传菜、订单进度、退菜动态、划菜记录。中间不重复显示档口和模式标题，订单卡随可用宽度排成多列，卡片按内容决定高度；只显示实际备注，右侧数量与划菜操作保持紧凑。模式、档口和订单来源分别选择；切换模式不会切换档口。KDS 使用独立操作界面，左侧不设置“返回收银”入口。

标准划菜按桌／订单展示，以当前开台会话 `tableSessionId` 汇总堂食订单及加菜，跨次用餐的同桌号不会合并；旧 API 或历史订单缺少会话标识时保守地按原订单分卡。自取、商家配送始终按原订单分卡。支持单菜划完、指定每个菜品的部分数量，以及整桌／整单批量完成。整桌／整单只提交当前档口范围内可制作的剩余任务；搜索定位订单卡，不会隐藏该卡在当前档口的其他菜品。点击时冻结任务、版本和数量并立即提交；后续加菜不会加入已经发出的批次。请求处理中禁止重复点击，结果不确定时保留同一请求键及清单，仅允许重试该次操作。明确拒绝会显示失败并刷新。

汇总划菜按档口、商品、名称、销售单位、菜品备注及顾客备注汇总相同菜品，右侧逐原任务填写各桌／订单数量。两个模式使用同一份厨房进度。份、串、杯等单位在任务创建时保存，此后菜单改单位不影响已有任务。混合单位的总计不标成“份”。

## 份数与流程

- 01 桌 3 份、02 桌 2 份同菜，可分别填写本次数量。仅 01 桌填 2 后，剩余待做 1、待传 2，02 桌不受影响。
- 部分、汇总全部、整桌／整单划菜均点击立即提交，无确认窗。汇总模式的“全部”指选中的菜品组；整桌／整单指当前所选档口范围内该次用餐／订单的可制作任务。
- 堂食制作完成进入待传菜；“待传菜”中按原菜品数量传出，可只传部分；订单进度只查看制作及传菜状态，不提供数量输入或传菜按钮。制作、传菜不触发收款／结账。
- 自取和商家配送接单后进入厨房，菜品支持部分划菜、部分传菜。所有原订单菜品在全部档口均制作并传出后，服务端事务内进入 READY；只做完、只传部分或其他档口尚缺菜均不会提前进入交付。“全部传菜”只处理当前桌／订单当前档口已经做好的未传数量，不包含尚未制作的菜，不会提前完成交付。
- 自取继续现有取餐码和收银完成流程；配送继续现有待配送、开始配送、送达和收银流程。厨房详情只保留菜品、厨房备注、数量、制作与传菜操作，不展示顾客电话、地址、额外取餐信息、包装勾选或取餐配送链接。
- KDS 开启后，受 KDS 管理的自取／配送不能从原收银入口绕过整单制作与传菜检查。入厨前已经 READY／DELIVERING 的历史单继续原交付，不要求重做。
- 收银人员新增堂食菜品沿用“通知制作”，只通知新增数量；顾客自动报厨、非堂食接单与 KDS 任务均可在无打印机、打印功能关闭时工作。未开启 KDS 门店保留原打印规则。
- 加菜不重置已完成量；退菜先移除未制作数量，涉及已做／已传的部分明确记录。原 OrderItem 删除、财务结账、页面重开不删除厨房历史。
- 厨房直接使用全部／部分划菜，不要求先点“开始制作”；厨房不发起“催菜”，只接收催菜标识。保留新增数量提示、超时、搜索、撤销本人可撤回的制作操作。份数已发生后续传菜、打包、退菜或其他变更时不能撤销旧操作。

2026-10-13 厨房操作调整：移除厨房屏的“开始制作”“催菜”按钮，减少出菜前的多余点击。划菜后记录完成数量。当前没有多工序和等叫配置，不另设重复的待制作菜单。催菜应由前台发起，URGE 接口和厨房催菜标识保留；当前尚未补前台催菜按钮。划菜记录包含制作、传菜、打包、撤销及收银交付。

暂停 KDS 期间由收银完成的非堂食交付，在重新开启时以独立 HANDOFF 事件结清原厨房任务；不会伪装为厨师划菜记录，也不会要求重新制作。

## 数据和接口

| 对象 | 用途 |
|---|---|
| KdsSetting | 门店开关、启用时间、超时、档口及分类映射 |
| KdsTask | 原订单菜品的制作／传出份数、单位、备注、档口及版本 |
| KdsOperation | 操作人、请求编号、动作、原订单归属和数量变化历史 |
| Order.kdsPackedAt | 厨房整单出餐完成的兼容交付标记，亦兼容旧打包路径；数量变化会失效 |

任务的 OrderItem ID 是保留历史的逻辑引用，不建立随菜品删除的级联关系。订单与商家保持关联；操作行保存名称、单位、桌号、订单号及档口快照。

| 接口 | 用途 |
|---|---|
| GET /merchant/kds | 当前任务、订单进度、设置、分类、最近 200 条操作 |
| PATCH /merchant/kds/settings | 店主／经理配置 |
| POST /merchant/kds/actions | START／MAKE／SERVE／URGE，逐行 taskId、version、quantity |
| POST /merchant/kds/pack | 所有档口完成且三项打包核对通过 |
| POST /merchant/kds/undo | 撤回本人仍可撤回的操作 |

写入按订单 ID 固定顺序加锁，KDS 事务使用 READ COMMITTED，任务版本再次校验，变更与操作历史同事务提交。重复请求用 requestKey 和载荷校验处理，多台屏幕操作同一旧版本只有一次成功。批量中任何一行冲突则全部回滚，不能部分提交。

每次请求重新核实员工当前状态与角色、商家归属与启用状态。其他商家任务不可操作；普通员工不可改厨显配置。
