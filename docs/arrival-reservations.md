# 预约到店 V1

实现日期：2026-10-19。用户已确认采用预约到店方案，并明确取消可约限制。用户随后授权提交、推送并上线 API、收银、商家后台与 KDS；小程序由用户手动上传体验版。发布状态与凭证见 [发布记录](release/arrival-reservations-20261019-v1.md)。

## 范围与页面

商家详情原“到店自取”入口升级为“预约到店”，提供打包自取和到店用餐；只开启一种时直接进入对应流程。小程序原有自取菜单、商品和结算链接统一进入预约流程，已保存的自取购物车自动升级并保留餐品。

- 打包自取：选菜 → 尽快取餐或选择时间 → 联系信息 → 提交 → 商家确认 → 商家开始制作 → 待取餐 → 交付。
- 到店用餐：时间、人数、联系方式 → 可选提前选菜 → 提交 → 商家确认 → 到店核对餐品、安排空闲桌台 → 原桌账、扫码加菜和统一结账。
- “我的订单”增加“我的预约”页签，包含堂食预约及自取预约。堂食有独立预约详情；自取订单详情显示预约时间、进度和取餐码。
- 收银增加 `/reservations`，支持待处理／已结束／全部、日期、方式、联系电话筛选，以及确认、拒绝、提出改约、入座、标记未到店和查看自取订单／桌账。电脑列表和详情分别滚动；手机采用列表进入详情。
- 商家后台“店铺设置 → 到店预约”分别控制两种预约。新开关默认开启，仍受原堂食／自取能力、认领状态和平台经营总开关控制；不修改原能力开关。

## 预约规则

没有按营业时间、座位容量、时段单量、提前预约时长、固定三天范围或人数上限限制预约。只校验未来有效时间、正整数人数、有效联系方式和餐品可售性；人数仍受数据库整数存储范围保护。已休息的门店可以接收预约，最终由商家确认。

时间保存为 UTC，选择及展示固定按越南时间。堂食必须选择时间；自取可选尽快。默认选择约 30 分钟后的时间仅用于方便填写，不是提前时长限制。

待商家确认时顾客可以取消；已确认后改时、取消联系商家。商家提出新时间时保留原时间，顾客同意后生效；拒绝则保持原时间。旧页面对已经被替换的时间提议不能操作。堂食入座和自取开始制作均会阻止尚未完成确认的改时。

未到店由商家在约定时间之后手动处理，不自动取消、不自动收费。商家确认和入座不校验预约容量；入座时检查真实桌台归属、启用状态和当前桌账，避免并发把两组客人加入同一桌。

## 订单、厨房与财务

自取沿用 `Order`，新增 `isReservation`、`scheduledFor`、`proposedScheduledFor`。历史订单默认 `isReservation=false`，保持原流程。预约接单停留在 `ACCEPTED`；前端不连带开始制作，KDS 补偿同步也不会提前创建任务。显式开始制作后再触发既有打印及厨房同步。

堂食新增 `DiningReservation`。预选菜按提交时的真实价格、名称、数量和备注保存快照，提交时检查顾客看到的金额。预约阶段不创建订单、桌账或厨房任务。入座事务按桌台锁顺序锁定并关联一个桌账，预选菜只转入一次；重复入座返回原结果。原顾客后续扫码加菜复用该桌账中自己的订单。已由商家接待的预约桌可在公示营业时间以外继续扫码点餐。

堂食预选菜在入座时复查供应与价格；变化时提示重新联系确认，不静默替换或涨价。实际报厨继续由原桌账的“通知厨房”操作完成。餐品制作与付款保持独立，沿用现有线下收款和 KDS 无结账门禁规则。

堂食预约 `SEATED` 的完成状态从关联桌账关闭状态派生，作废桌账显示取消。预约本身不产生营业额，正式餐品进入订单后才参与原结账和报表。

自取纸质小票与 KDS 显示预约取餐时间；小票包含取餐码。历史非预约小票不添加预约字段。

## 幂等与提醒

创建预约使用用户范围内的请求键；堂食并发请求和购物车消费处于同一事务，对写冲突重试。小程序按用户、商家和方式保存草稿及未确认结果的原请求。断网时保留请求及餐品快照，重开后重试查询原结果，避免重新创建预约。

两类预约都在收银列表中提醒待确认。已确认自取在预约时间前约 30 分钟（尽快单立即）显示备餐提示，使用 API 返回时间判断，不依赖设备时钟。该提示不自动启动厨房，也不限制商家提前操作。

堂食预约复用现有 Web Push 订阅、持久事件和重试队列；新增预约外键，原订单外键改为可空并保留历史数据。发送前检查待确认状态、订阅所属商家及员工有效性；跳转独立预约页面。后台推送仍依赖原 VAPID 和手机授权，单测不代表真机锁屏通知验收。顾客端使用订单／预约详情刷新获取状态，未添加微信订阅消息。

## API

| 接口 | 用途 |
| --- | --- |
| `POST /reservations` | 提交堂食预约，可消费预选菜购物车 |
| `GET /reservations`、`GET /reservations/:id` | 当前顾客的堂食预约 |
| `POST /reservations/:id/cancel` | 取消待确认堂食预约 |
| `POST /reservations/:kind/:id/reply-time` | 顾客同意或拒绝某个时间提议 |
| `GET /merchant/reservations` | 当前商家的两种预约，附服务端时间 |
| `POST /merchant/reservations/:kind/:id/actions` | 商家确认、取消、建议改时、入座、未到店 |
| 原 `/orders`、`/merchant/orders` 接口 | 自取创建、制作、交付与收款 |

`:kind` 为 `DINE_IN` 或 `PICKUP`。顾客和员工接口分别限制账户类型，所有读写受用户／商家归属约束。

## 迁移与发布

迁移：`apps/api/prisma/migrations/20261019160000_arrival_reservations/migration.sql`。增加预约表和字段，扩展提醒事件外键，不更新或删除历史订单、收款、厨房任务及原服务开关。

发布顺序：备份 → 执行迁移 → 更新 API → 更新收银、商家后台及独立 KDS → 上传并验收小程序。新版小程序需要新 API 返回两种预约能力；只上传小程序无法完成这次升级。

旧 API 回退前需要保留新预约和提醒数据，不能删除新增表或强制把已经出现的空订单外键改回非空。发布过程不需要创建生产测试订单。
